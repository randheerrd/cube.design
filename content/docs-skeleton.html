Skeleton

New Last updated Nov 2026

Grey placeholders shown while content is loading. They mirror the shape of the real content (text lines, values, charts, avatars), so the page feels faster and doesn’t jump when data arrives. Use the base shapes to build any layout, or a ready-made pattern.

Guidelines Specifications Code (not in Storybook yet) Accessibility (coming soon)

At a glance

A skeleton holds the place of content that is still loading. It is built from three grey shapes — Text, Block and Circle — arranged to mirror the real layout, so when data arrives the real content replaces it in place and nothing jumps.

Use it for

Regions that load data: widgets, tables, cards, lists — on first load or a refetch.

Built from

① Base shapes (Shape = Text · Block · Circle) → ② Patterns: Text lines, List item, Table cell, Card, Plan card.

Not a skeleton

Button actions: a spinner in the button. Long background tasks: a progress toast. No data: an empty state.

How skeletons are built

Every loading state is made from instances of one component, Skeleton, so a colour or radius change happens in one place. Use a ready-made pattern when it fits the content; otherwise arrange base shapes to match the real layout.

① Base shapes

Skeleton · Shape = Text (a line of text, 12 tall, radius 4), Block (images, charts, buttons, values — radius 6) or Circle (avatars, logos, icons). Resize them to match the real content.

② Patterns

Composed from the base shapes for common content: Text lines (1 / 2 / 3 — last line half width), List item (avatar + 2 lines), Table cell, Card (title, value, caption, chart) and Plan card (matches Subscription card).

Skeleton or another loading state?

Use skeletons for regions that load data — mirror the real layout so nothing jumps when data arrives. Use a spinner inside a button for actions, a progress toast for long background tasks, and an empty state when loading finishes with no data.

NeedUse
A region loads data on first load or a refetch (widget, table, card, list)Skeleton — a pattern or base shapes
The user started an action with a buttonA spinner inside the button
A long task runs in the backgroundA progress toast
Loading finished with no dataAn empty state
Loading failedAn empty state or a message — never leave the skeleton

Anatomy

A skeleton is built from three simple grey shapes arranged to mirror the real content. Patterns combine them for common layouts.

1 · Card pattern

How a loaded card maps to skeleton shapes (at 1.6×).

#ElementNotes
1Title lineShape = Text, half width — the metric name.
2Value blockShape = Block, 150 × 32 — the big number.
3Caption lineShape = Text, half width, 10 tall — the delta / comparison.
4Chart blockShape = Block, full width — the chart or image.

2 · Base shapes

Shape = Text · Block · Circle.

#ElementNotes
1Text12 tall (match the text line height), radius 4. Width ≈ expected text length; last line of a paragraph ~50%.
2BlockAny size, radius 6. Values, buttons, images, charts, chips.
3CircleSquare sizes (24 / 32 / 40), radius 100. Avatars, logos, icons.

Base shapes

Skeleton has one variant property, Shape. Size comes from resizing the instance; the shape stretches.

Shape

Text default

One line of text. 12 tall, radius 4. Width ≈ the expected text length.

Block

Values, buttons, images, charts, chips. Any size, radius 6.

Circle

Avatars, logos, icons. 24 / 32 / 40, radius 100.

Size (resize the instance)

Text 8–16 tall · Block any · Circle 24 / 32 / 40. There is no size property — resize the instance to match the real content.

Patterns

Ready-made loading layouts composed from the base shapes. Swap one in when it fits the content.

Text lines · Lines

1 default

One line of text.

2

Full line + half line.

3

Two full lines + half line. Resize width freely.

List item · Table cell

List item

Avatar / icon + two text lines. Use for lists, dropdown options, chat history.

Table cell

Value + sub-value in a 52px table cell. Drop into a table column’s Column-cells slot, one per cell.

Card · Plan card

Card

Generic widget / metric card loading: title, value, caption, chart area.

Plan card

Loading state for the plan card in the plans grid or cart. Matches Subscription card.

Common layouts

The skeleton sits in the same container as the real content and is replaced in place when data arrives.

Do’s and don’ts

Five rules. Each pair shows the right and wrong way, and why.

Do

Match the skeleton to the real layout. No jump when content loads; users see what’s coming.

Don’t

Don’t use one generic block for everything. The layout jumps and users can’t predict the content.

Do

Show a realistic number of rows. It feels like the real list.

Don’t

Don’t fill the screen with endless skeleton rows. It looks heavy and broken.

Do

Vary line widths; make the last line shorter. It reads like real text.

Don’t

Don’t make every line full width. It looks like a striped block, not text.

Do

Offtake

Keep the real headers and labels that are already known. Users get context while numbers load.

Don’t

Don’t skeleton static labels and buttons. It hides information the page already has.

Do

Use skeletons for content regions. They’re made for data loading.

Don’t

Don’t use skeletons for button actions. Use a spinner in the button instead.

How to add one in Figma

Design a loading state in four steps.

  1. Start from the loaded design
    Duplicate the finished frame (widget, card, table) — the skeleton must have the same size and layout.
  2. Use a pattern if one fits
    Card, Plan card, List item, Table cell, Text lines — swap them in.
  3. Otherwise replace with base shapes
    Text → Shape = Text (same width as the text, ~50% for last lines). Numbers, charts, images, buttons → Block. Avatars, logos → Circle. Keep static labels as real text.
  4. Annotate for developers
    Shimmer animation, show after ~300ms, how many rows, and what replaces it on error / no data (empty state).

Before you hand off

  • Skeleton matches the loaded layout and size.
  • Patterns used where they fit.
  • Static labels kept as real text.
  • Realistic number of rows.
  • Shimmer, delay and error / empty fallback annotated.

WhenFirst load or refetch of a region. Not for button actions — use a spinner in the button.
DelayShow the skeleton after ~300ms, so fast responses don’t flash.
AnimationA shimmer: a lighter sweep (White @60%) moving left → right, 1.2–1.5s.
Reduced motionRespect prefers-reduced-motion: the shapes stay static.
SwapReplace in place, at the same size. No layout jump.
CountShow the expected number of rows — e.g. 5–10 table rows, not 50.
