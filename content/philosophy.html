01 — Philosophy

Built by designers who have to live with the decision the next morning.

Principles tell you what to do. Philosophy tells you why, so you can work out what to do when no principle covers the case in front of you. Six beliefs, in the order they matter.

Why this exists Six beliefs Counted How to use it

/ Where this came from

GobbleCube builds software that tells people what to do about their business. That is a heavier promise than most software makes, and it changes what good design means here.

A product that merely displays data can afford to be beautiful and vague. A product that recommends a price change, flags a stockout or predicts next week's demand cannot. Every screen we draw either earns a decision or wastes someone's morning.

So this is not a style guide. It is the shared answer to one question — what do we believe about the people on the other side of the screen — written down so it can be argued with rather than assumed.

/ Core beliefs

Six beliefs, in the order they matter

Each one has cost us something to learn. They are listed in priority order: when two of them conflict, the lower number wins.

/01

We design decisions, not dashboards

The unit of value is not a chart. It is a person changing their mind, or confirming it fast enough to move on. Before any layout exists, we can name the decision, who makes it, how often, and what they do today instead.

This kills a whole class of work. "Give the user visibility into inventory" is not a brief — it is a shrug. "Help a category manager decide which twelve SKUs to reorder before Thursday's cutoff" is a brief, and it tells you what to put on screen and what to leave off.

/02

Confidence is a design material

We ship predictions. A prediction rendered in the same type, weight and colour as a recorded fact is a lie of formatting. Whenever the machine is guessing, the interface says so — and says how hard it is guessing.

This is not a disclaimer in grey 11px at the bottom. Uncertainty is laid out with the same care as the number itself: ranges instead of false points, sample sizes where they are small, an honest "not enough data" where that is the truth.

/03

Density is respect

Our users are experts operating the same screens for six hours a day. Consumer minimalism — one number per card, endless whitespace, a wizard for everything — insults them and costs them scrolling. Give an expert more per screen, arranged well, not less arranged prettily.

Density is not clutter. Clutter is undifferentiated. Dense done right means a strong visual hierarchy doing the work that whitespace does in consumer software: weight, alignment, hairlines and restraint with colour.

/04

The interface should shrink as trust grows

A new user needs the explanation, the breakdown, the "why am I seeing this." A user in month nine needs the answer and a keyboard shortcut. Designs that serve only the first day become furniture the rest of the year.

So we build the explanation as something that can recede — collapsible, on demand, remembered per user — rather than a permanent tax on the fluent. The same feature should be able to feel like a tutorial and like a cockpit.

/05

We design the recovery, not the happy path

The happy path designs itself; it is the first thing anyone draws. The product is actually made of the other states — the feed that failed overnight, the SKU with no history, the forecast that was confidently wrong last week and has to be faced this week.

A flow is not designed until someone can get out of it. Every automated action has a manual override, every recommendation can be dismissed with a reason, and every error tells the user what to do next rather than what went wrong internally.

/06

Latency is a design problem

A query that takes nine seconds is a design failure before it is an engineering one, because we chose to ask for it. Speed is not something engineering adds afterwards — it is a constraint we design inside, like screen width.

Practically: we design what the screen looks like at 200ms, at 2s and at 20s, and we treat a skeleton that never resolves as a bug in the design. If the honest answer is slow, the design says so and lets people go do something else.

/ The short version

We would rather show less and be trusted than show more and be checked.

/ In the work

Three places this earns its keep

A handbook that only gets read in week one is a document. One that gets cited on a Wednesday is a tool.

/01

In critique

Cite a principle by number instead of saying "it feels off." "This breaks 04 — the model's confidence isn't visible" is a reviewable claim. "I'd maybe make it lighter?" is not.

/02

In review gates

The Craft Bar is the checklist for design review. If a screen has no empty state, it does not pass, regardless of how good the populated state looks.

/03

In onboarding

A new designer reads this end to end in week one and runs a Frame session in week two. If that is not true, the handbook is wrong and we fix the handbook.

Beliefs are what you fall back on. Rules are what you cite.
