Components

Input

Stable Last updated Oct 2026

A single-line or multi-line text field, in three sizes and five states. Pick a size and decide which optional parts — prefix, suffix, helper text — the field needs; the Specifications tab lists every token.

Guidelines Specifications Code (opens Storybook in a new tab) Accessibility (coming soon)

At a glance

Three decisions set every field: what kind of value it takes (Type), how much room it has (Size) and what it needs to tell people (label, helper, prefix, suffix and validation). Get those right and the rest — states, colour, spacing — comes from the component.

A required label, a placeholder that shows the format, and one line of helper text — the setup most fields need.

1 · Type

Default for one value, Text area for a paragraph, Chips for a list of tokens.

2 · Room

Medium (default) almost everywhere, Large for hero forms and mobile, Small in dense tables and filters.

3 · Feedback

A visible label always; helper text before the mistake; a specific error after it.

Anatomy

Every type shares one anatomy: a label, an input row with an optional prefix and suffix, and an optional helper message. Shown: Default / Medium with prefix, suffix and helper text. Width is parent-driven — the field fills its container.

Prefix & suffix

Two optional slots sit inside the input row. Both accept any icon component. Use them to tell people what kind of value belongs here, not to decorate. A field has exactly one trailing slot — swap its content for the current status instead of adding a second icon.

Chips & overflow

When Type = Chips, the input row hosts removable chip instances instead of free text. Chips wrap until the field’s width is exceeded; beyond that, collapse the overflow into a single “+N more” chip rather than letting the field grow vertically. The threshold isn’t enforced by the component — it’s a layout convention that depends on the field’s width and each chip’s label length.

Field label*
Mango Pineapple Strawberry

Chips fit

Up to about 3 chips fit comfortably on a medium-width field. All remain individually removable.

Field label*
Mango Pineapple +4 more

Overflow

Beyond the field’s width, hidden chips collapse into “+N more”; tapping it opens an overflow menu with the rest.

Validation & errors

A field moves through a predictable sequence. Designing and building to the same one keeps every form in the product behaving the same way.

3 · Correct

Error replaces the helper text and says what to fix.

RuleWhy
Validate on blur or submit, not on every keystroke.Telling someone they’re wrong before they’ve finished typing is noise.
Once a field is in Error, re-validate as they type and clear it the moment it’s valid.The error should never outlive the problem.
Error text replaces helper text — it doesn’t stack under it.The helper row is one line. Two lines of small text are unreadable.
Never signal an error with colour alone.The border, the warning icon and the message together make it perceivable without colour.
Set Error text = false only when a message sits elsewhere (e.g. a form-level summary).The icon alone doesn’t say what to fix.

Do’s and don’ts

Labels & helper text

Do

Email*

Keep a visible label. It stays on screen while typing and is the field’s accessible name.

Don’t

Don’t rely on the placeholder alone. It disappears as soon as the person types and isn’t a label.

Do

Password*

At least 8 characters

Put format rules in helper text so people know them before they type.

Don’t

Password*

Don’t put instructions in the placeholder. They vanish the moment typing starts.

Errors

Do

Email*

Don’t

Don’t say only that something is wrong. “Invalid” gives no way to recover.

Layout & sizing

Do

First name*
Last name*

Use one size per row or group so heights and baselines line up.

Don’t

First name*
Last name*

Don’t mix sizes side by side. Mismatched heights look like a layout bug.

  • Use Text area only when the value can genuinely run long — a description, a comment.
  • Don’t use Chips for a single value — that’s a plain Default field.
  • Don’t let a Chips field grow vertically to fit every chip; collapse the overflow.
  • Don’t style a border, radius or height by hand “just for this form”. Every size already has its own spec.
  • Don’t leave a field in Error after the value has been fixed.

Writing content

  • Label — a short noun phrase: “Work email”, “Daily budget”. Always visible; never replaced by the placeholder.
  • Placeholder — an example of the expected value (“name@company.com”), not instructions.
  • Helper text — one short line of guidance shown before a person makes a mistake.
  • Error text — replaces the helper once validation fails and states what to fix: “Enter a valid email address”, not “Invalid”.
  • Required — mark a field required only when submitting without it is genuinely blocked.

Behavior & accessibility

TopicWhat to do
KeyboardTab moves focus into and out of the field; the focus ring must always be visible. In Chips, Enter turns the typed text into a chip and Backspace on an empty field removes the last one.
LabelThe label is the accessible name. Pass label even when design hides it, and don’t replace it with a placeholder.
RequiredisMandatory sets aria-required="true" on the input as well as showing the asterisk.
ErrorsLink the error message to the input with aria-describedby and set aria-invalid="true" while in Error, so screen readers announce it.
DisabledNot focusable and not submitted. If someone needs to read the value but not edit it, use a read-only presentation instead.
Touch targetsPrefer Large on mobile. Small is for pointer-driven, dense desktop UI only.
WidthWidth is parent-driven. Make sure the container is wide enough for the longest expected value and the label.
