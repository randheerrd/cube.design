02 — Principles

Eight rules with teeth, and the stated exception to every one.

A principle is only useful if it can lose an argument for you. A rule with no stated exception gets ignored entirely the first time it is inconvenient — so each of these carries its own.

The anatomy Eight rules When each bends

/ What a principle is for

These are not aspirations. Each one is written so that it can be cited by number in a critique and settle the question.

That is a high bar. It means a principle has to be specific enough to be broken visibly, and honest enough to admit where breaking it is correct. A rule that only ever agrees with whoever is speaking is not a rule.

Cite the number, not the feeling. "This breaks 04" is reviewable. "It feels off" is not.

/ The anatomy

Every rule has three parts

Drop any one of them and the rule stops working: it becomes a slogan, an opinion, or a thing people route around.

/01

What it means

One sentence. If it takes a paragraph to state, it is a policy, not a principle.

/02

In practice

Four things you can point at in a file. This is the half that makes it reviewable rather than quotable.

/03

When it bends

The stated exception, written in advance — so bending it is a decision somebody made, not an excuse somebody found.

/ The eight

What we hold each other to

In no priority order — unlike the beliefs, these do not outrank one another. One of the eight has no exception at all.

/01

Show the work

Every number on screen can be traced to where it came from, in one interaction.

  • Aggregates open into their components
  • Every metric has a definition a user can read without leaving the page
  • "As of" timestamps on anything derived from a pipeline
  • Recommendations name the two or three inputs that drove them

/02

One decision per screen

A screen answers one question. Everything else on it is context for that question.

  • You can state the screen's question in one sentence
  • One primary action, visually unambiguous
  • Secondary actions are quieter, not merely smaller
  • If two decisions genuinely co-occur, they are two views

/03

Default to the boring pattern

Novelty is a cost paid by every user, forever. It has to buy something.

  • Check the design system before drawing anything new
  • A table is usually the right answer; say why it is not
  • New patterns come with a written case and a system contribution
  • Consistency beats local optimisation across the product

/04

Make the machine's certainty visible

Predicted, estimated and recorded values never look alike.

  • A consistent visual language for forecast vs. actual, used everywhere
  • Ranges over false precision — no four decimal places on a guess
  • Low-confidence output is labelled at the point of use, not in a footnote
  • "Not enough data" is a designed state, not an empty cell

/05

Glance, scan, dig

Three depths, always in that order, on every dense surface.

  • Glance — is anything wrong? Readable in two seconds
  • Scan — where is it? Sorting, grouping, hierarchy
  • Dig — why? Detail on demand, never pre-loaded onto the page
  • Test the glance layer by squinting at it, literally

/06

Never block on the AI

Every automated path has a manual one beside it.

  • Model down, slow or unsure — the user can still do the job by hand
  • Recommendations are dismissible, and dismissal is cheap
  • Bulk actions always have a per-item override
  • No modal whose only exit is waiting for inference

/07

Words are the interface

Copy is design work, written by the designer, not borrowed from the schema.

  • Labels use the user's vocabulary, not the database column name
  • Buttons name their verb — "Approve order", never "Submit" or "OK"
  • Errors say what to do next, in second person
  • No placeholder copy reaches a review, ever

/08

Four states or it does not ship

Empty, loading, error, and too-much-data are part of the design, not edge cases.

  • Empty — first-run and genuinely-nothing are different states
  • Loading — designed for 200ms, 2s and 20s
  • Error — partial failure shown per component, not a blank page
  • Overflow — 10,000 rows, 90-character names, negative numbers

/ The test

A rule you cannot lose an argument to is decoration.

Why every principle below carries its own exception

/ The exceptions

When each one bends

Written in advance, in one place, so the first inconvenient case does not quietly retire the rule.

/01 Show the work

When the derivation is genuinely not explainable — some model outputs are not — say that plainly rather than inventing a tidy rationale. A fabricated explanation is worse than an honest "this is a model score."

/02 One decision

Triage screens are a real exception — a queue exists precisely to hold many decisions at once. There, the single question becomes "which of these do I handle first", and the screen is designed to answer that.

/03 Boring pattern

Where the boring pattern actively misleads. A standard line chart on sparse, irregular data implies a continuity that is not there — inventing something more honest is worth the cost.

/04 Certainty

It does not. This is the one principle with no exception — if we cannot show the uncertainty, we have not finished designing the feature.

/05 Glance, scan, dig

Single-purpose detail views — an audit log, a single order — start at dig. Adding a summary layer to something a user opened deliberately is padding.

/06 Never block

Where the manual path is genuinely dangerous — a destructive bulk operation with no undo. There, blocking is the safer design, and the wait gets a progress state and a cancel.

/07 Words

Regulated or contractual language that must appear verbatim. Reproduce it exactly and design around it — do not paraphrase legal text to make it prettier.

/08 Four states

Internal tooling with a handful of known users can ship with the states stubbed — but the stub is written down as debt, with an owner, not quietly forgotten.

Rules decide what good looks like. The process decides when anyone may call it done.
